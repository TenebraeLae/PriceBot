# ТЗ: витрина по прайсу (PriceBot)

Закон продукта. Источник — промпт инженера (Telegram-бот + Mini App + Excel-синк + оплата). Правки поведения — только через этот файл, затем код. Чат ТЗ не заменяет.

## 1. Цель

Живой контур закупщика в Telegram: поиск и карточки товара из PostgreSQL, Mini App-витрина, серверная корзина, заказ с уникальным номером, QR на оплату, статусы и уведомления. Админ загружает Excel — каталог пересобирается в БД; файл прайса не читается в рантайме поиска.

Пользователь — клиент/закупщик в Telegram. Админ — владелец прайса (`ADMIN_IDS`).

**Критерий «готово» (продукт):** `docker compose up` поднимает бота, API, Postgres, Redis; админ загрузил Excel → поиск в боте и Mini App видит те же sku/цены/фото; корзина → итог → QR → fake-webhook → заказ «оплачен» + уведомление; повтор webhook не дублирует; 1000 параллельных поисков по API без лавины 5xx (есть отчёт p50/p95); секреты не в git.

Нагрузка v1: пик до 1000 одновременных поисков/открытий карточек без блокировки event loop и без «один запрос — один полный скан Excel».

## 2. Входы и выходы

**Входы**

- Telegram Bot API (сообщения, ReplyKeyboard, WebApp-кнопка, webhook или long polling).
- Telegram Mini App `initData` на каждый запрос API.
- Excel (.xlsx) от админа (бот или админ-роут FastAPI).
- Платёжный webhook / ручной `get_status`.
- Переменные окружения (`.env`, не коммитить).

**Выходы**

- Сообщения бота на русском (меню, карточки, заказы, поддержка, уведомления).
- JSON API Mini App (каталог, корзина, чекаут, QR, статусы).
- Каталог и заказы в PostgreSQL; горячий кэш Redis (опционален, путь в БД обязателен).
- Файл прайса на диск (`data/imports/`) для аудита.
- QR (байты PNG > 0), payload = URL/СБП-строка провайдера.
- Отчёт импорта админу (ok/err, первые ошибки).
- Выгрузка каталога обратно в Excel.
- Nightly `pg_dump` в `data/backups/` (ротация N дней).

**Не выходы v1:** публичный веб-магазин вне Telegram; Google Sheets / 1С / МойСклад как истина; облачные SaaS-каталоги; allow_paid_broadcast; неофициальные API.

**Точки входа**

- Бот: `pricebot.bot.main:main` — локально long polling; в Docker/проде webhook Telegram на FastAPI. Один процесс не блокирует другой.
- Веб: `pricebot.web.main:app` — Mini App, REST каталога/заказа/оплаты, webhook платежа, админ-загрузка Excel.

## 3. Сущности и статусы

Часовой пояс всех календарных дат: `Europe/Moscow` (`TIMEZONE`). Не «примерно».

### Пользователь

- `telegram_id` (PK), `username`, `first_seen_at`, `status`: `active` | `blocked`.
- Mini App: `initData` → тот же `telegram_id`. Тело запроса не подменяет личность.

### Категория

- `id`, `name`, `sort`, `active`.

### Товар

- `sku` (unique), `name`, `category_id`, `description`, `price` (Decimal, не float), `stock` (Decimal ≥ 0), `unit` (как в прайсе: шт/кг/мешок/…), `photo_url`, `active`, `sort`, `import_id`.
- Наличие: `stock > 0` → «в наличии»; `stock = 0` → «нет».
- Нет файла фото — плейсхолдер, карточка живая.

### Импорт

- `id`, `filename`, `admin_id`, `started_at`, `finished_at`, `rows_ok`, `rows_err`, `status`: `pending` | `applied` | `rejected`.
- Успех: полная пересборка **активного** каталога из валидных строк + `import_id`.
- 0 валидных строк — `rejected`, старый каталог не трогать.

### Корзина

- Одна на `telegram_id`: позиции (`product_id`, `qty`), `updated_at`.
- На чекауте цены **снимок** в заказ; клиентская цена игнорируется.

### Заказ

- `number` вида `PB-YYYYMMDD-XXXX` (уникальность в БД, суффикс суточный порядковый).
- `user_id`, позиции (`sku`, `name`, `qty`, `price_snapshot`), `total`, `promo_code`, `status`, `created_at`, `paid_at`, `note`.
- Статусы (пользователю по-русски):
  - `awaiting_payment` — ожидает оплаты
  - `paid` — оплачен
  - `processing` — в обработке
  - `done` — выполнен
  - `cancelled` — отменён
  - `error` — ошибка
- Бот не показывает `paid` / `done` без факта платёжного модуля или явной отметки админа (для `processing`/`done`/`cancelled`).

### Платёж

- `order_id`, `provider`, `provider_payment_id`, `amount`, `status`, `raw_payload`, `created_at`.
- Статусы: `created` | `pending` | `succeeded` | `failed` | `expired`.
- Один `provider_payment_id` обрабатывается один раз (идемпотентность).

### Промокод

- `code`, `kind`: `percent` | `fixed`, `value`, `starts_at`, `ends_at`, `max_uses`, `used_count`, `active`.
- Один код на заказ. Невалидный код — отказ, не молчаливая скидка 0.
- Валидный промо, из-за которого итог < 0: **clamp `total` к 0** (заказ бесплатный, не отказ).

### Обращение в поддержку

- `ticket`, `user_id`, `message`, `admin_reply`, `status`: `open` | `closed`.

### Событие / уведомление

- Пользователю в чат: заказ создан / оплачен / в обработке / выполнен / ошибка.
- Админу: новый заказ и успешная оплата.

## 4. Правила и инварианты

1. **Excel ≠ истина в рантайме.** Поиск и карточки только из PostgreSQL (+ опциональный Redis). Хендлер `/start` и поиск файл не открывают. Холодный Redis не ломает поиск (путь в БД).
2. **Цены и остатки** считаются на сервере. Mini App не доверяет клиенту. `initData` проверяется на каждый API-запрос.
3. **Валюта:** RUB. Цены и суммы — `Decimal`.
4. **Поиск:** по `name`, `sku`, `category`; регистронезависимо; подстрока. Пустой/пробельный запрос **не** сканирует каталог: пустая выдача + подсказка категорий / «введите запрос». Запрос длиннее 200 символов — пустая выдача без 500 (`query_too_long`). Строка вида `%' OR 1=1` — литерал, не SQL.
5. **Пагинация:** бот `PAGE_SIZE=10`, Mini App `PAGE_SIZE_WEB=20`. `page < 1` или страница за EOF — пустые `items`, не 500. Порядок стабильный: `sort ASC`, затем `sku ASC`.
6. **Неактивный товар** не в поисковой выдаче и не добавляется в корзину.
7. **Импорт Excel.** Обязательны колонки `sku` + `name` + `price` (синонимы RU/EN). Лишние колонки игнорировать. Нет обязательных заголовков — файл не принят, каталог цел. Отрицательный `stock` — ошибка строки (не молча). Нечисловая/пустая/`бесплатно` цена — ошибка строки. Цена должна быть `> 0`. Дубль `sku` в одном файле: первая валидная строка принимается, последующие — ошибка. Битые строки в отчёт, импорт применяется если `rows_ok ≥ 1`. `rows_ok = 0` — reject, старый каталог цел. После успеха — инвалидация Redis. Потолок строк файла: `MAX_IMPORT_ROWS=50000`; больше — reject файла. Сохранённый файл — аудит, не runtime.
8. **Синонимы колонок (минимум):** `sku`/`артикул`/`код`; `name`/`название`/`наименование`; `category`/`категория`; `description`/`описание`; `price`/`цена`; `stock`/`остаток`/`количество`; `unit`/`единица`/`ед`; `photo`/`фото`/`image`/`картинка`; `active`/`активен`; `sort`/`сортировка`/`порядок`.
9. **Корзина:** `qty ≤ 0` — отказ; `qty > stock` — отказ; неактивный sku — отказ. Итог = серверный пересчёт `Σ(qty × server_price)` минус промо.
10. **Чекаут:** проверка остатков на сервере; нехватка — отказ позиции, заказ не создаётся «в минус». Два параллельных чекаута не списывают одну единицу сверх `stock` (блокировка строки товара). Двойной тап «оплатить» = один платёж на заказ.
11. **Номер заказа** уникален в БД (`PB-YYYYMMDD-XXXX`).
12. **Оплата:** адаптер `PaymentProvider` (`create_payment`, `get_status`, `parse_webhook`, `verify_signature`). Выбор: `PAYMENT_PROVIDER=fake` (HMAC `X-Payment-Signature`) или `yookassa` (`YooKassaPaymentProvider`, официальный `POST/GET https://api.yookassa.ru/v3/payments`). ЮKassa: HMAC нет; `verify_notification(client_ip, body)` = IP allowlist + повторный GET платежа. `create_payment`: RUB, `capture=true`, `confirmation.type=redirect`, payload = непустой `confirmation.confirmation_url` (карты demo-магазина; СБП QR — только боевой магазин). Не размазывать ЮKassa/СБП/Robokassa по хендлерам. Без успешного webhook/`get_status` заказ не `paid`. Плохая подпись/уведомление — 401/403, БД не меняется. Replay того же `provider_payment_id` — идемпотентен. Сумма webhook ≠ `total` заказа — платёж/`заказ` в `error`/`failed`, не `paid`. Секрет webhook Telegram ≠ секрет платёжки.
13. **QR:** содержимое = payload/URL платежа. Пустой контур не пишется. Файл/байты > 0. Сканер читает тот же payload.
14. **Промо:** процент или фикс, срок, лимит использований, один код на заказ. Просрочен / исчерпан / неверен / неактивен — отказ.
15. **Блок user:** поиск и чекаут отказывают.
16. **Админы:** только `ADMIN_IDS` из env. Не-админ не загружает Excel и не меняет статусы.
17. **Rate limit Telegram:** 25–30 исходящих req/s (AIORateLimiter или Redis). На 429 (`RetryAfter`) — retry с уважением `retry_after` + лог. `allow_paid_broadcast` выключен в v1.
18. **Фото:** URL или путь в `data/media/`; отдача API/статик. Пустая строка → нет фото (хелпер `resolve_product_photo`). HTTP(S) URL отдаётся как есть; карточка без фото живая.
19. **Тексты UI** — русские, короткие, без английских заглушек. Маркетинг витрины нейтральный, бренд заказчика не выдумывать.
20. **Рестарт контейнеров** не теряет состояние Postgres.

## 5. Сценарии пользователя

1. `/start` — приветствие и главное меню (ReplyKeyboard + кнопка Mini App).
2. Меню v1: 🛒 Каталог (Mini App) · 🔎 Поиск · 📦 Мои заказы · ℹ️ Информация · 📞 Поддержка. Текст вне меню = поисковый запрос.
3. Поиск в боте: PostgreSQL → страницы `PAGE_SIZE` → карточка (фото если есть, цена, наличие, краткое описание) → «В Mini App» / «В корзину» (корзина на сервере).
4. Mini App: категории, поиск, пагинация, карточки с фото из БД, количество, корзина, итог, оформление, QR, статус заказа. Свой API, не «бот шлёт Excel». Ресайз и быстрый ввод не ломают UI; чекаут при ошибке ввода запрещён.
5. Оформление: остатки → заказ с номером → платёж → QR + сумма + номер. Нехватка — отказ, не уход в минус.
6. Мои заказы: текущие и прошлые, статус по-русски, повтор QR пока `awaiting_payment`.
7. Уведомления: создан / оплата получена / в обработке / выполнен / ошибка.
8. Поддержка: сообщение → админ в боте → ответ → пользователь видит ответ. Без внешнего helpdesk.
9. Информация: статичный текст из `content/` или слотов БД, не роман в хендлере.

## 6. Сценарии админа

- Загрузить Excel в бота или админ-роут FastAPI (только админ).
- Отчёт синка (ok/err, первые ошибки).
- Успешный импорт → каталог обновлён, поиск сразу видит новые цены/остатки (инвалидация Redis).
- Заказы: поиск по номеру, `telegram_id`, sku; фильтр по статусу; смена статуса + уведомление пользователю.
- Пользователи: просмотр; блок (поиск и чекаут отказывают).
- Промокоды: создать / выключить.
- Уведомления о новых заказах и успешных оплатах.
- Выгрузка текущего каталога в Excel (тот же набор полей).

## 7. Цепочка статусов (приёмка)

```
каталог: Excel → parse → (0 ok → rejected, каталог цел)
                      → (≥1 ok → applied, активный каталог = валидные строки)

корзина → checkout (остаток ок, промо ок) → заказ awaiting_payment + платёж created
        → QR(payload)
        → webhook verify + amount==total → платёж succeeded, заказ paid, уведомления
        → replay webhook → no-op (идемпотентно)
        → webhook amount≠total → error, не paid
        → без webhook → не paid

paid → (админ) processing → (админ) done
awaiting_payment → (админ/юзер по правилам) cancelled
```

## 8. Критерии приёмки

- Доменные инварианты §4 покрыты тестами; хендлеры не содержат своей «истины» по цене/остатку/промо/оплате.
- Админ загрузил валидный xlsx → поиск «цемент М500» в боте и Mini App показывает тот же sku/цену/наличие.
- Пустой/битый Excel / 0 валидных строк — старый каталог цел.
- Mini App без `initData` / битая подпись / чужой bot token — 401, корзина не пишется.
- Чекаут не уходит в минус по stock; номер уникален; двойной тап = один платёж.
- Fake-webhook с верной подписью переводит в «оплачен»; повтор — идемпотентен; плохая подпись — 401/403.
- QR: байты > 0, payload = платёж.
- 1000 параллельных GET поиска — нет лавины 5xx, p50/p95 в отчёте; Excel на запрос не открывается.
- `docker compose up` + restart не теряет Postgres; Redis down — поиск из БД.
- Секреты только в `.env`.

## 9. Вне скоупа v1

Веб-магазин вне Telegram с аккаунтами. 1С / МойСклад / Google Sheets как обязательная интеграция. ИИ-рекомендации, OCR накладных, мультисклад, курьерская логистика, ЧПУ/CAD. Неофициальные API, чужие кассы, обход 429. Боевой провайдер, захардкоженный в хендлерах. Scaffold Mini App с кнопками-заглушками (после этапа C). MSI/десктоп. `allow_paid_broadcast`. Копирование вёрстки stemsbot / чужого магазина. Клонирование кода BiblioBot/SellBOT/SaleBot.

## 10. Команды разработки

Стек (не менять): Python ≥ 3.11, aiogram 3, FastAPI, SQLAlchemy 2 + asyncpg, PostgreSQL 16, Redis, pydantic-settings, httpx, openpyxl, qrcode[pil], aiohttp / uvicorn, pytest + pytest-asyncio + ruff. Деплой: Docker Compose, Ubuntu VPS. UI — русский; идентификаторы кода — английские.

```
uv sync
uv run pytest -q
uv run ruff check pricebot tests
docker compose up --build
```

Локально: polling. Прод: webhook. `PAYMENT_PROVIDER=fake` в тестах. Живая ЮKassa: `PAYMENT_PROVIDER=yookassa` + shop id/secret из кабинета (не в git).

Мониторинг: `GET /metrics` (счётчики HTTP). Нагрузка: in-process SQLite или `--base-url` на живой API/Postgres.

### Адверсари (писать и гонять)

Импорт: пустой файл / нет колонок / цена «бесплатно» / stock −1 / дубли sku / огромный файл; 0 валидных — каталог цел; частично валидный — только ok + отчёт.
