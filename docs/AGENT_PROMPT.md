ОГРАНИЧЕНИЯ
- Не scaffold и не экраны-заглушки: каждая заявленная функция реально работает end-to-end (хотя бы на FakePaymentProvider).
- Excel — источник загрузки, не источник истины в рантайме. Поиск и карточки — только из PostgreSQL (при необходимости горячий кэш Redis). Файл прайса на диск/в объектное хранилище сохранять для аудита, но не читать его в хендлере /start.
- Секреты только в `.env` (не коммитить). API-ключи платёжки, токен бота, `WEBAPP_URL`, `ADMIN_IDS` — из окружения.
- Telegram Bot API + свой FastAPI. Никаких облачных SaaS-каталогов, Google Sheets как истины, «откройте в 1С и пришлите разработчику».
- Не использовать неофициальные, украденные API, чужие ключи, обход ограничений Telegram или платёжки.
- Rate limit: глобально 25–30 исходящих запросов/сек к Telegram (AIORateLimiter или эквивалент на Redis). На 429 (RetryAfter) — автоматический retry с уважением `retry_after`, плюс лог.
- Масштаб каталога: нельзя строить меню из сотен кнопок. Поиск + пагинация + категории обязательны.
- Даты и статусы заказа — календарные дата/время в TIMEZONE, не «примерно».
- Бот не показывает заказ оплаченным/выполненным без факта из платёжного модуля (или явной отметки админа в оговорённом статусе).
- Mini App не доверяет клиенту: цена, остаток, скидка считаются на сервере. Подпись `initData` Telegram проверяется на каждый запрос API.
- Хостинг-профиль v1: VPS 2+ vCPU / 4 ГБ RAM / NVMe, Ubuntu 22.04/24.04, автозапуск после ребута (Compose + restart policies / systemd).

ДОМЕН (зафиксировать и не упрощать до «бот нашёл строку в Excel»)
Каталог из импорта, поиск, корзина, заказ, платёж, уведомления, админ-синхронизация прайса.

Параметры (зафиксированы, не спрашивать):
- валюта: RUB; единицы каталога — как в прайсе (`unit`: шт/кг/мешок/…); цены — decimal, не float;
- идентификация пользователя: Telegram ID — первичный ключ; в Mini App — `initData` → тот же telegram_id;
- поиск: по названию, артикулу (sku), категории; регистронезависимо; пустой запрос не сканирует весь каталог (показать категории / «введите запрос»);
- пагинация: `PAGE_SIZE=10` в боте, `PAGE_SIZE_WEB=20` в Mini App;
- наличие: `stock > 0` → «в наличии»; `stock = 0` → «нет»; отрицательный stock в импорте — ошибка строки, строка не молча импортируется;
- фото: URL или относительный путь в `data/media/`; отдавать через API/статик; нет файла — плейсхолдер, карточка живая;
- заказ: уникальный человекочитаемый номер `PB-YYYYMMDD-XXXX` (уникальность в БД, не «случайная надежда»);
- статусы заказа (пользователю по-русски): `awaiting_payment` ожидает оплаты · `paid` оплачен · `processing` в обработке · `done` выполнен · `cancelled` отменён · `error` ошибка;
- статусы платежа: `created` / `pending` / `succeeded` / `failed` / `expired`; один `provider_payment_id` обрабатывается один раз;
- оплата: доменный адаптер `PaymentProvider` (`create_payment`, `get_status`, `parse_webhook`, `verify_signature`). В v1 — один провайдер через `PAYMENT_PROVIDER` + `FakePaymentProvider` для тестов. QR: содержимое = payload/URL платежа от провайдера (СБП или страница оплаты), не «картинка без данных». Не размазывать ЮKassa/СБП/Robokassa по хендлерам;
- итог заказа: сумма позиций (qty × server_price) − промо (если есть) = `total`; клиентская цена игнорируется;
- промокоды v1: процент или фикс, срок действия, лимит использований, один код на заказ; невалидный код — отказ, заказ без молчаливого «0»;
- Excel-синк: полная пересборка активного каталога из валидных строк файла + версия импорта (`import_id`); битые строки — в отчёт админу, не роняют весь импорт, если есть хотя бы одна валидная (если валидных 0 — импорт отклонить, старый каталог не трогать);
- колонки прайса (минимум, заголовки RU/EN синонимы): `sku`, `name`, `category`, `description`, `price`, `stock`, `unit`, `photo`, `active`, `sort`. Лишние колонки игнорировать. Нет `sku`+`name`+`price` — файл не принят;
- админы: `ADMIN_IDS` в `.env` (ротация через env, не «админ админов» в UI в v1);
- бот в проде: webhook; локально: polling. Секрет webhook Telegram и секрет платёжки — разные;
- allow_paid_broadcast — не в v1 (слот в конфиге можно оставить выключенным);
- бэкап БД: nightly `pg_dump` в `data/backups/` (ротация N дней), описать в инструкции.

Сущности и статусы (минимум):
Пользователь: telegram_id, username, first_seen_at, status active/blocked.
Категория: id, name, sort, active.
Товар: sku (unique), name, category_id, description, price, stock, unit, photo_url, active, sort, import_id.
Импорт: id, filename, admin_id, started_at, finished_at, rows_ok, rows_err, status pending/applied/rejected.
Корзина: user_id, позиции (product_id, qty), updated_at; на чекауте цены снимок в заказ.
Заказ: number, user_id, items (sku, name, qty, price_snapshot), total, promo_code, status, created_at, paid_at, note.
Платёж: order_id, provider, provider_payment_id, amount, status, raw_payload, created_at; идемпотентность по provider_payment_id.
Промокод: code, kind percent|fixed, value, starts_at, ends_at, max_uses, used_count, active.
Обращение в поддержку (v1 минимум): ticket, user_id, message, admin_reply, status open/closed.
Событие/уведомление: order created / paid / processing / done / error — в чат пользователю; админу — новый заказ и успешная оплата.

Тексты: операционные по-русски ясно и коротко (поиск пуст, нет в наличии, ошибка оплаты, заказ создан). Не оставлять английские заглушки в UI бота и Mini App. Маркетинговые тексты витрины — нейтральные, не выдумывать бренд заказчика.

ФУНКЦИОНАЛ
Пользователь:
1) /start — приветствие и главное меню (ReplyKeyboard + кнопка Mini App).
2) Меню (v1): 🛒 Каталог (открывает Mini App) · 🔎 Поиск · 📦 Мои заказы · ℹ️ Информация · 📞 Поддержка. Текстовое сообщение вне меню = поисковый запрос (сценарий «цемент М500»).
3) Поиск в боте: запрос → PostgreSQL → страницы по PAGE_SIZE → карточка (фото если есть, цена, наличие, краткое описание) → «В Mini App» / «В корзину» (корзина живёт на сервере, одна на telegram_id).
4) Mini App (основной UX, как stemsbot): категории, поиск, пагинация, карточки с фото из БД, количество, корзина, итог, оформление, QR оплаты, статус заказа. Всё через свой API, не через «бот шлёт Excel».
5) Оформление: проверка остатков на сервере → создание заказа с уникальным номером → создание платежа → показ QR + сумма + номер заказа. Если товара не хватает — отказ позиции, заказ не создаётся «в минус».
6) Мои заказы: текущие и прошлые, статус по-русски, повторный показ QR пока `awaiting_payment`.
7) Уведомления в бот: заказ создан, оплата получена, в обработке, выполнен, ошибка.
8) Поддержка: пользователь пишет → админ получает в боте → отвечает → пользователь видит ответ. Без внешнего helpdesk.
9) Информация: статичный текст из `content/` или таблицы слотов, не зашитый роман в хендлере.

Админ (ADMIN_IDS):
- загрузить новый Excel в бота или в админ-роут FastAPI (защита: только админ);
- увидеть отчёт синка (ok/err, первые ошибки);
- при успешном импорте каталог обновлён, поиск сразу видит новые цены/остатки (инвалидация Redis);
- просмотр заказов: поиск по номеру, telegram_id, sku; фильтр по статусу; смена статуса (с уведомлением пользователю);
- просмотр пользователей; блок (поиск и чекаут отказывают);
- промокоды: создать/выключить;
- уведомления о новых заказах и успешных оплатах;
- выгрузка текущего каталога обратно в Excel (тот же набор полей).

Платежный контур:
- create → webhook/callback → verify_signature → идемпотентная обработка → заказ `paid` → уведомления;
- повтор webhook того же платежа не меняет заказ повторно;
- get_status — для ручного/фонового дожима, если webhook потерялся;
- QR после create_payment; файл/байты QR > 0, payload читается сканером как URL или СПБ-строка.

АДВЕРСАРИ-ТЕСТЫ (писать и гонять, не «потом»)
Цель — опровергнуть каталог, заказ, оплату и нагрузку, не подтвердить их. Минимум:
- импорт: пустой файл / нет обязательных колонок / цена «бесплатно» / stock −1 / дубли sku / огромный файл; 0 валидных строк — старый каталог цел; частично валидный — применены только ok, ошибки в отчёте;
- поиск: пустая строка, SQL-метки в запросе (`%' OR 1=1`), слишком длинный запрос, неизвестный sku, неактивный товар не в выдаче;
- пагинация: page < 1, page за EOF — пусто без 500; стабильный порядок (sort, sku);
- карточка: нет фото — не 500; цена из БД, не из query-string;
- Mini App: без initData / битая подпись / чужой bot token — 401, корзина не пишется; telegram_id из тела запроса не подменяет initData;
- корзина: qty 0 / −1 / 999999 при stock 2 — отказ; неактивный sku нельзя добавить; итог = серверный пересчёт;
- промо: просрочен, исчерпан, неверен, фикс больше суммы (итог не отрицательный — зафиксируй в ТЗ: отказ или clamp к 0 и тестируй одно);
- заказ: два параллельных чекаута — не два списания одной единицы сверх stock; номер уникален;
- оплата: без webhook — статус не paid; плохая подпись — 401/403, БД не меняется; replay того же payment_id — идемпотентен; сумма webhook ≠ total заказа — error, не paid;
- QR: пустой контур не пишется; файл > 0 байт; payload совпадает с payment;
- админ: не-админ не загружает Excel и не меняет статусы; блок user → поиск/чекаут отказ;
- Telegram: burst сверх лимита не долбит API без паузы; RetryAfter уважается;
- нагрузка: 1000 параллельных GET поиска — нет 5xx лавины, p95 в отчёте; Excel не открывается на запрос;
- рестарт контейнеров не теряет Postgres-состояние; Redis cold start не ломает поиск (есть путь в БД);
- UI: ресайз Mini App, быстрый ввод, экспорт/чекаут при ошибке ввода запрещён.

После каждого этапа: юнит-тесты на домен + smoke API/хендлеров без живого Telegram и без боевой кассы + ручной прогон когда токен есть. Если адверсари нашёл дыру — чини до следующего этапа. Не объявляй этап закрытым «на глаз».
